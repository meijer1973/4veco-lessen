# L2.0 Student-Web House-Style Baseline

Date: 2026-05-25
Status: DRAFT BASELINE FOR HUMAN REVIEW

## Scope

This baseline applies to future Book 1 student-web paragraph builds that follow
the `1.1.1` through `1.1.3` pilot pattern. It does not approve broad scaling;
it defines what must remain true before Scale Gate 1 may consider controlled
production.

## Route Layers

Student paragraph landings should use a controlled route, not a peer-level
artifact dump.

| Layer | Purpose | Visibility rule |
|---|---|---|
| `Start` | Orientation, instapquiz, voorkennis. | Show only when start artifacts exist. |
| `Leer` | Core explanation/skills route. | Show when the main skills explanation exists. |
| `Oefen` | Guided support plus scoped practice games. | Show when guided practice or scoped practice routes exist. |
| `Check` | Non-summative exit-ticket checkpoint. | Hide until a reviewed exit-ticket surface exists. |
| `Verdiep` | Summary, news/context, presentation, textbook, downloads, full skill map. | Keep secondary/collapsed where possible. |
| `Oefen gemengd` | Consolidation/gemengde-opgaven mixed practice. | Use for consolidation paragraphs that mainly contain mixed exercises. |

## Companion Completion Contract

A complete standard paragraph may eventually include:

- voorkennis or start check;
- uitleg vaardigheden;
- begeleide inoefening;
- scoped `Redeneren`, `Rekenen / stappenplan`, and `Grafieken` practice routes
  where relevant;
- summary/news/presentation/textbook resources in `Verdiep`;
- a non-summative exit ticket after L1.7B-R/GATE-L1.7B.

The landing page must not show every possible artifact as a primary card. It
must answer the student question: "What should I do next?"

## Dual-Coding Baseline

For visual, graph, table, formula, or diagram skills:

- procedure parity is necessary but not sufficient;
- every core procedure needs a visible worked learning object;
- guided practice must use source visuals that match the exercise labels,
  values, and answer route;
- screenshot QA must check semantic visual adequacy, not only overflow.

## Procedure Baseline

- Student-facing routes must use ordinary labels, not internal PV/MTU IDs.
- Formal step IDs may exist in data and validators but must stay out of
  visible route copy.
- Procedure steps must match between skills explanation, guided practice,
  presentation, and practice game where the procedure is shared.

## Game-Row Baseline

The current second-row game set is pilot-ready with flags, not scale-ready.

- `Redeneren`: acceptable as controlled pilot reasoning practice; richer
  variants and replay depth remain future work.
- `Rekenen / stappenplan`: acceptable as a procedure/calculation-step route;
  it is not a full numeric calculation engine.
- `Grafieken`: acceptable as an MVP with at least one less-labelled graph task;
  more independent axis/grid-reading variants are required before graph-heavy
  scaling.
- All three routes must consume the shared skill-map route language.
- No route may imply diagnostics, mastery, sequencing, grading, summative use,
  student-facing AI, PV projection, or PV machine promotion.

## Exit-Ticket Readiness

Exit-ticket work remains paused until L1.7B-R. The future MVP must:

- be source-controlled platform code;
- use shared skill-map compact checkpoint mode;
- present 3-5 non-summative tasks;
- give neutral feedback and practice suggestions only;
- avoid score/pass/mastery/evidence/adaptive-focus language;
- activate landing-page `Check` only for paragraphs with reviewed output;
- pass student-experience, teacher-learning-quality, screenshot/interaction,
  and boundary review.

## Screenshot And QA Baseline

For future scale gates, screenshot QA should sample route patterns, not only
individual pages:

- ordinary theory paragraph with `Start`, `Leer`, `Oefen`, `Verdiep`;
- graph-heavy paragraph with `Grafieken`;
- paragraph without graph route;
- consolidation/gemengde-opgaven paragraph with `Oefen gemengd`;
- paragraph with `Check` after exit ticket exists;
- desktop, mobile width, light, dark, keyboard/focus reachability where
  relevant.

## Quality-Ref Baseline

Quality refs should separate:

- Part A textbook evidence;
- companion/student-web evidence;
- human-review status;
- surface-by-surface status;
- carried flags and fixed flags.

`PASS WITH FLAGS` means a surface is usable for the stated controlled scope,
has no open hard fails, and carries explicit non-blocking flags. It does not
mean scale-ready, final-reviewed, or clean PASS.
