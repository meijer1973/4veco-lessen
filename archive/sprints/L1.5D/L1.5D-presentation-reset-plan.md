# L1.5D Presentation Reset Plan

Date: 2026-05-12  
Target: `1.1.1 Schaarste en economisch denken`  
Working title: **Presentation v2: one authored deck, two polished outputs**

## 1. Diagnosis

The current PowerPoint-to-web path should not become the scaling baseline.

The problem is architectural, not just visual:

- the `.pptx` is treated as source truth for web;
- the converter tries to infer semantics from positioned slide fragments;
- later fixes added sidebar labels, card detection, mobile patches, notes toggles, and overflow safety nets;
- every new issue invites another converter/CSS patch instead of a better design model.

This is why the result keeps feeling like a patched conversion instead of a beautiful authored HTML presentation.

## 2. Reset Decision

Open a narrow reset sprint:

**L1.5D-R: Presentation Reset for §1.1.1**

Do not keep extending the current `presentatie-v1` converter as the baseline. Keep it only as a fallback for legacy/generated artifacts while the reset is built.

The new baseline is:

> A single platform-owned presentation source model generates both the editable PowerPoint and the web presentation.

The web presentation is not a reverse-engineered PPTX. The PPTX is not hand-built separately. Both are products of the same semantic slide source.

## 3. Product Standard

The new presentation must feel like a real classroom deck:

- authored, not converted;
- beautiful at first glance;
- usable by a teacher at the board and by a student reviewing on a laptop or phone;
- one main idea per slide;
- large readable visual objects;
- no generic card-grid grammar;
- no boxed prose as the default design language;
- no mobile clipping hidden by `overflow-x: hidden`;
- speaker notes available as a narration-ready panel; no separate student/teacher mode labels;
- editable PPTX output preserved.

## 4. Lesson-Specific Design Brief

Audience: VWO 4 students, age 15-16.  
Use context: live classroom explanation plus later student review.  
Tone: clear, warm, slightly editorial, not corporate.  
Design promise: **students feel the tension of choosing before they learn the formula.**

Core visual idea:

> Every slide shows that a choice has a visible path and an invisible path you leave behind.

Suggested motif:

- split-path compositions for Lisa and the farmer;
- one recurring "not chosen" accent line;
- large euro amounts when money is the evidence;
- compact B02 route visual instead of repeated explanation cards;
- soft classroom palette: ink, warm paper, economic orange, teal/green for alternatives, restrained dark slide only where contrast helps.

Avoid:

- default website cards;
- dashboard styling;
- decorative blobs/orbs;
- slide screenshots pasted into a web shell;
- tiny text that survives audits but fails actual classroom use.

## 5. Proposed Slide Arc

Use 9-10 slides, with more space and less density than the current deck.

1. **Cover:** `Kiezen kost altijd iets`  
   Hook with the €20 vs €27 tension, not a generic title page.

2. **Lisa's choice:** cinema or book  
   Large two-option scene. Learning goals appear as a compact strip: schaarste herkennen, alternatieve kosten bepalen, nettowaarde beoordelen.

3. **Schaarste:** needs are bigger than means  
   One visual equation: behoeften > middelen -> kiezen.

4. **Alternative costs:** the best thing you do not choose  
   Show chosen path and best missed path. Keep price vs missed opbrengst distinct.

5. **B02 route:** four steps  
   Alternatives -> opbrengsten -> rangschik -> nettowaarde. This should be a memorable route/flow, not a stack of cards.

6. **Farmer evidence:** tarwe versus maïs  
   One clean editable table or field comparison with 10 hectares and winst per hectare.

7. **Farmer decision:** what is missed and what remains  
   Show alternative costs and nettowaarde as a visual subtraction.

8. **Pitfall slide:** price is not automatically alternative cost  
   Short contrast: "betaalde prijs" versus "beste gemiste opbrengst".

9. **Retrieval:** three checks, not five dense cards  
   Students answer: what is scarce, what is missed, what is the net value?

10. **Bridge:** why §1.1.2 matters  
   How do we compare differences in money and percentages?

## 6. Architecture

Create a new platform-owned presentation source model, for example:

- `build-scripts/content/book-1/b1-111-presentation-v2.js`
- `build-scripts/lib/presentation-model.js`
- `build-scripts/lib/render_presentation_pptx_v2.js`
- `build-scripts/lib/render_presentation_html_v2.js`
- `engines/presentation-v2.css`
- `engines/presentation-v2.js`

Each slide record should contain:

- `id`
- `navTitle`
- `teacherTitle`
- `studentTitle`
- `layout`
- `blocks`
- `visualRefs`
- `speakerNotes`
- `accessibility`
- `pptxHints`
- `htmlHints`

The model must support semantic blocks such as:

- `choiceComparison`
- `conceptEquation`
- `procedureRoute`
- `workedTable`
- `valueSubtraction`
- `pitfallContrast`
- `retrievalPrompt`

The HTML renderer uses the semantic blocks directly. It must not parse PPTX coordinates to recover meaning.

## 7. Prototype Before Build

Before implementing the full deck, build three proof slides:

- cover;
- Lisa choice slide;
- B02 four-step route slide.

Render each as:

- editable PPTX;
- desktop HTML screenshot;
- 390px mobile HTML screenshot.

Review these first. If they do not feel beautiful, stop and redesign the visual system before producing the other slides.

Prototype iteration note, 2026-05-12:

- user accepted the v2 direction as a major improvement;
- scale the default stage to the effective 80% view that fits the laptop screen;
- prefer a stable widescreen slide canvas whenever the viewport allows it;
- keep a narrow/mobile option when widescreen plus controls would not fit;
- show speaker notes in a right-side reading rail on wide screens, falling back below on narrow screens;
- keep the speaker notes as teacher-style narration text because they may later drive text-to-speech or video export.
- add browser-based slide-canvas QA: every important rendered element must fit inside the visible slide frame across desktop, wide notes, fullscreen, and mobile screenshots.
- keep unit codes such as B02 internal to the repository; student-facing presentation text uses the full skill name, for example "Alternatieve kosten in een keuze-situatie".
- add dark mode as a real presentation theme and include dark screenshots in the browser QA gate.

## 8. Implementation Procedure

1. Freeze current `presentatie-v1` as legacy/fallback.
2. Write the presentation source model for the three prototype slides.
3. Build the HTML v2 renderer from semantic blocks.
4. Build or adapt the PPTX renderer from the same model.
5. Run teacher/student/visual review on the three-slide prototype.
6. Only after prototype approval, finish the full 9-10 slide deck.
7. Regenerate `presentatie.html` and `presentatie.pptx` through the platform workflow.
8. Update paragraph validation so `presentatie-v2` is the expected baseline.
9. Add regression tests for the semantic blocks and rendered mobile screenshots.
10. Retire `presentatie-v1` from the scaling path.

## 9. Review Team

Use the complete review team before calling this a baseline:

- lead reviewer: source truth, parity, gates, no patchwork;
- teacher reviewer: classroom sequence, board readability, speaker notes;
- student reviewer: clarity, navigation, mobile review experience;
- visual reviewer: beauty, hierarchy, rhythm, no generic templates;
- accessibility reviewer: text size, contrast, keyboard, reduced motion, no clipping;
- testing reviewer: validators, screenshots, PPTX audit, reproducibility.

## 10. Acceptance Tests

Required technical gates:

- `node scripts/validate-paragraph.js --mode complete "<1.1.1 paragraph>"`
- `node scripts/deploy.js "<Boek 1 target>"`
- targeted Jest tests for `presentation-v2`
- browser slide-canvas QA: `node scripts/qa-presentation-v2-html.js "<presentation-v2 html>" "<screenshot dir>"`
- PPTX accessibility audit: no text below 14pt, no contrast violations
- PPTX roundtrip/render to PDF or slide PNGs
- HTML screenshots:
  - desktop 1200x900;
  - tablet width;
  - mobile 390px;
  - mobile 360px;
  - light and dark mode if supported.

Required quality gates:

- no slide requires hidden overflow to look acceptable;
- no body-level horizontal scroll;
- no text clipping in screenshots;
- no slide uses "title + three cards" by habit;
- PPTX and HTML contain the same lesson content and notes;
- speaker notes are explicit, narration-ready, and do not use student/teacher mode labels;
- no internal unit codes such as B02 appear in generated student-facing presentation HTML or narration;
- light and dark theme screenshots pass the slide-canvas QA gate;
- sidebar labels come from `navTitle`, not inferred text;
- screen-reader structure preserves choice comparisons and tables;
- review verdict is PASS or PASS WITH FLAGS with no blockers.

## 11. Stop Conditions

Stop and redesign instead of patching if:

- the prototype needs more than two layout-specific CSS exceptions;
- the HTML needs to infer structure from the PPTX;
- the PPTX and HTML drift in wording or procedure steps;
- mobile requires clipping or hidden overflow to pass;
- teacher/student reviewers say the slides are understandable but ugly;
- any review team member returns FAIL.

## 12. Outputs

Platform outputs:

- presentation v2 source model;
- PPTX renderer;
- HTML renderer;
- presentation v2 CSS/JS;
- tests and validators.

Generated lesson outputs:

- `1.1.1 Schaarste en economisch denken – presentatie.pptx`
- `1.1.1 Schaarste en economisch denken – presentatie.html`
- refreshed `index.html` links if needed;
- `1.1.1-presentatie-v2-review.md`;
- updated sprint review/roadmap note.

## 13. Scaling Rule

Do not use the current §1.1.1 web presentation as the L1.4 scaling baseline.

Only scale after:

1. the three-slide prototype passes teacher/student/visual review;
2. the full §1.1.1 deck passes the complete review team;
3. the same source model generates both PPTX and HTML cleanly;
4. L1.4 proves the v2 system on §1.1.2 without one-off patches.
