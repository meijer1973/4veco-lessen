# Sprint L1.7B-P23: Exit Ticket Target-Skill Checkpoint Designs For 1.1.2 And 1.1.3

Date: 2026-05-26
Status: STOP/HANDOFF READY; HUMAN REVIEW REQUIRED

## Goal

Decide whether reviewed exit-ticket checkpoint designs can be produced now for:

- `1.1.2 Percentages en indexcijfers`
- `1.1.3 Grafieken en tabellen`

The sprint must either prepare generated-checkpoint-ready designs that cover the
target-exercise operation chains, or stop with a precise platform handoff for
unsupported task types. It may not turn calculation or graph/table readiness
into weak generic choice checks.

## Context

`specifications/product-end-state.md` says the exit ticket should help decide
whether the student is ready to try the paragraph target exercise. The current
`1.1.1` checkpoint does not prove that the exit-ticket system can handle
calculation, unit notation, graph reading, graph drawing, interpolation, or
constructed reasoning.

`L1.7B-MAP` closed PASS WITH FLAGS and fixed metadata alignment for `1.1.1`,
but it kept `targetReadinessEvidence: false`. `L1.7C-MATH` restored the
primary math route, so the visible `Rekenen` route is no longer blocking this
sprint. The remaining question is whether the current exit-ticket engine and UI
can express the target-skill checks for `1.1.2` and `1.1.3` without weakening
the specification.

## Quality Standard

The expected outcome is not the smallest acceptable artifact. The expected
outcome is a complete, coherent, student-usable implementation of the stated
specification within the authorized scope.

The work must meet the specification first. If implementation scope is bounded,
the quality floor inside that scope remains full quality. Missing parts of the
full product must be named as follow-up work, blockers, or explicit human
waivers.

A result is not done because files exist, tests pass, or a surface renders. It
is done only when generated output, rendered output, student-facing affordance,
metadata, answer model, and proof all match the specification. For this sprint,
that means a stop/handoff decision is preferable to generated output that hides
missing calculation, unit, graph/table, or constructed-response capability.

## Operationalized sprint procedure

1. Read the stable specifications, L1.7B-MAP records, paragraph plans, target
   exercise records, and current engine/UI support.
2. For `1.1.2`, decompose the target exercise into old/new value selection,
   percentage-change calculation, index-number calculation, index-point versus
   percentage distinction, final notation, and explanation requirements.
3. For `1.1.3`, decompose the target exercise into table reading, economic axis
   convention, graph drawing, graph reading, interpolation, percentage-claim
   evaluation, and explanation requirements.
4. Compare those operation chains with the current exit-ticket task schema and
   UI. If the current engine cannot support the required task types, stop and
   write a platform handoff. Do not generate misleading choice-only output.
5. Confirm that no `1.1.2` or `1.1.3` exit-ticket source/generated output is
   active and that landing `Check` activation remains reviewed-output-only.
6. Record validation evidence, technical QA, and a human-review packet. The
   human review must decide whether the stop/handoff is acceptable or whether
   another path is required before L1.7B-P23 can close.
