Date: 2026-05-23
Status: ACTIVE PLAN

## Purpose

Define the complete paragraph companion set and decide whether the existing
exit-ticket prototype can become the non-summative checkpoint surface for that
set.

L1.7B is a foundation-hardening sprint. It may produce an MVP only if the
prototype source-control state, product-use boundaries, and shared skill-map
dependency are safe. It must not add another surface blindly.

## Work Procedure

1. Confirm repository cleanliness and current roadmap state.
2. Inspect the prototype zip in a temp directory only. Do not import it by
   accident and do not commit the untracked zip.
3. Inventory prototype contents, runnable tests, product language, storage
   behavior, adaptive/PV boundaries, and integration notes.
4. Define the scalable paragraph companion set and surface hierarchy.
5. Define the exit-ticket MVP contract:
   - non-summative retrieval/checkpoint only;
   - paragraph target skills only;
   - compact checkpoint-mode skill-map use once L1.7C-0 exists;
   - no grading, mastery, diagnostics, adaptive routing, sequencing, AI,
     summative use, PV projection, or PV machine promotion.
6. Decide whether implementation is safe now.
7. If safe, implement through the platform workflow only:
   - add platform engine/generator source;
   - add source-controlled paragraph data;
   - regenerate lesson output through platform scripts;
   - update landing/validator rules only inside the platform workflow;
   - produce technical QA, screenshots, and human-review packet.
8. If not safe, record the stop decision and move the dependency to the next
   appropriate sprint.

## Stop Conditions

Stop before implementation if:

- the only prototype source is an untracked binary or cannot be reviewed as
  source-controlled code;
- the prototype claims or implies mastery, grading, diagnostics, adaptive
  routing, automatic sequencing, summative use, PV projection, or PV machine
  promotion;
- the exit ticket requires the shared skill-map engine before that contract
  exists;
- the MVP would duplicate future L1.7C-0/GAME-UX-1 architecture;
- implementation would require hand-patching generated lesson output;
- human-review records would be inferred from casual approval instead of a
  real review packet and interview.

## Validation Plan

For a contract-and-stop outcome:

- record git status in both repos;
- record prototype zip inventory and the result of its own smoke/unit test;
- record boundary-search results and implementation stop reasons;
- run no paragraph validators because generated output is unchanged.

For an MVP implementation outcome:

- run focused exit-ticket unit tests;
- run deploy/link/data checks;
- run paragraph complete student-web validation for the pilot paragraph;
- run Book 1 health;
- run v5 target-exercise count validation;
- run screenshot/interaction QA for desktop/mobile light/dark;
- run platform Jest or a stricter command named by the implementation plan;
- prepare student-experience and teacher-learning-quality review records.

## Out Of Scope

- Broad companion scaling.
- Three-aspect game-row upgrade.
- Shared skill-map engine implementation.
- Landing-page IA implementation beyond recording requirements.
- Target-exercise promotion to `reviewed_final`.
- Protected reference mutation or unit minting.
- Book 2 production.
- Diagnostics, adaptive routing, mastery, sequencing, student-facing AI,
  summative use, PV projection, or PV machine promotion.

## Expected Decision

The expected decision is that the current prototype is useful design evidence
but not safe to import as-is. If that is confirmed, L1.7B should pause
implementation, preserve the companion-completion contract, and make L1.7C-0
the next active dependency.
