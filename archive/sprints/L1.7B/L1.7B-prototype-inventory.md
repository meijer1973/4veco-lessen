## Useful Ideas

The prototype contains ideas worth preserving in a future, rewritten MVP:

- separate fields for calculation, answer, and unit;
- deterministic unit/answer checks for calculation tasks;
- short open-answer checks that produce feedback;
- a self-evaluation checklist after completion;
- randomized contexts for practice replay, provided deterministic QA fixtures
  are added;
- shell-generation pattern that resembles the current platform generator
  architecture.

## Boundary Problems

The prototype is not safe to import as-is.

Observed wording and behavior include:

- "target-exercise mastery check";
- "Mastery rule";
- "Mastery-eis";
- pass scores and phase thresholds;
- numerical score and percentage;
- "machine evidence" / copied result evidence;
- persistent best score in localStorage;
- adaptive-focus payload keys such as `4veco:adaptive:<parNr>`;
- task highlighting based on adaptive payload;
- `grade`, `gradePhase`, `finalize`, `passed`, and `passScore` API language.

These are incompatible with the L1.7B boundary:

```text
Exit ticket = non-summative retrieval/checkpoint game.
No grading, mastery, diagnostics, adaptive routing, sequencing, AI,
summative use, PV projection, or PV machine promotion.
```

## Source-Control Gap

Because the current prototype exists only as an untracked zip, reviewers who
work from GitHub cannot inspect it as part of the current repo state.

Before any implementation sprint can rely on it, one of these must happen:

1. Import a boundary-safe, reviewed source version through a platform sprint.
2. Rebuild the MVP from the inventory/spec without importing the zip.
3. Keep the zip as historical design evidence only and request a proper
   source-controlled prototype from the platform team.

## Integration Notes From Prototype

The prototype proposes platform integration points:

- copy `exit-ticket-engine.js`, `exit-ticket-ui.js`, and `exit-ticket.css`;
- add `build-exit-ticket-shells.js`;
- extend `scripts/deploy.js`;
- add `shared/exit-ticket/<parNr>.js`;
- add landing-page links/cards;
- add validator support if exit ticket becomes a required companion artifact.

Those are reasonable integration points, but the implementation must be
rewritten to satisfy the current boundary and shared skill-map architecture.
