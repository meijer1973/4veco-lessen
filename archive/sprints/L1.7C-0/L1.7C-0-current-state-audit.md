# L1.7C-0 Current-State Audit

Date: 2026-05-23
Status: CLOSED

## Summary

The platform already has a skill-tree engine and UI, but the current model is
not yet the shared aspect-filtered route layer needed for scalable companion
games.

Current useful foundation:

- `engines/skilltree-engine.js` stores local stars and can compute a next skill.
- `engines/skilltree-ui.js` renders a skill tree shell.
- `engines/skilltree/base-elements.js` derives interactive A-domain skill
  definitions from the MTU registry and generator coverage.
- `build-scripts/skilltree/build-skilltree-shells.js` emits paragraph-specific
  skill-tree shells and `shared/skilltree/<paragraph>.js` data.
- `build-scripts/content/paragraph/build-landing-page.js` already knows the
  three game aspects: `reasoning`, `calculation`, and `graphical`.

Main gap:

The skill-tree engine is currently a broad skill-tree product, not a scoped
route/progression service shared by the three practice games.

## Evidence

### Existing skill-tree modes

`engines/skilltree-engine.js` currently supports:

- `paragraph`
- `chapter`
- `module`

The `module` view is effectively an all-skill catalog. The UI labels this as
`Alles`.

L1.7C-0 needs a different public contract:

- `compact`
- `route`
- `full`

The existing all-skill view can inform `full`, but it must not be a student
default.

### Current active-skill data can expose too much

Current paragraph skill-tree data:

- `shared/skilltree/1.1.1.js` uses `activeSkills: null`, so all interactive
  A-domain skills are visible.
- `shared/skilltree/1.1.2.js` scopes to `A38` and `A39`.
- `shared/skilltree/1.1.3.js` scopes to `A61`, `A62`, `A63`, `A38`, and `A39`.

`activeSkills: null` is acceptable only for advanced/teacher/debug/full views.
It should not be the default route for a student practice game.

### MTU aspects exist but are not exposed by the skill-tree contract

The MTU registry already carries aspect data. Interactive A-domain generator
coverage currently includes 47 skills with these aspect counts:

| Aspect | Count |
|---|---:|
| `rekenen` | 42 |
| `verbaal` | 18 |
| `grafisch` | 15 |

Several skills are mixed-aspect, for example:

- `A02` has `rekenen` and `verbaal`
- `A05` has `grafisch` and `rekenen`
- `A07` has `grafisch`, `rekenen`, and `verbaal`
- `A61` has `rekenen` and `verbaal`
- `A62` and `A63` have `grafisch`

`engines/skilltree/base-elements.js` currently exposes skill id, name, layer,
dependencies, and description, but not `aspects`. L1.7C/GAME-UX-1 should expose
this metadata to make aspect-filtered routes possible.

### Game-row routes exist, but not shared skill-map consumption

Landing-page route cards already distinguish:

- `reasoning`
- `calculation`
- `graphical`

The practice games remain separate engines and should stay separate. The gap is
that they do not yet consume one shared scoped skill-map view. Each game risks
inventing its own progress/sidebar/route UI unless the shared contract is
implemented first.

### Exit ticket depends on compact route language

L1.7B recorded that the local exit-ticket prototype is design evidence only. It
uses mastery/score/pass/evidence/adaptive-focus semantics and is not
source-controlled. A later exit-ticket MVP must use the shared skill-map engine
only in compact checkpoint mode, with non-summative feedback and practice
suggestions.

## Audit Decision

L1.7C-0 can close as a contract sprint if it gives L1.7C and platform
`GAME-UX-1` enough detail to avoid three separate skill-tree UIs and to avoid a
student-facing full catalog by default.

No student output should be regenerated by this sprint.
