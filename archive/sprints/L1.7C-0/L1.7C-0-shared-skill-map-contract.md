# L1.7C-0 Shared Skill-Map Engine Contract

Date: 2026-05-23
Status: CONTRACT ACCEPTED FOR L1.7C / PLATFORM GAME-UX-1

## Core Decision

Build three practice engines plus one shared skill-map engine.

Practice engines:

- `reasoning-game-engine` for `Redeneren`
- `calculation-game-engine` for `Rekenen`
- `graphical-game-engine` for `Grafieken`

Shared support engine:

- `skill-map-engine`

The shared engine is not a fourth game. It is the common route, progression,
filtering, recommendation, and state-display layer used by the three games, the
exit ticket, and the paragraph landing page.

## Product Boundary

The shared skill-map engine may show practice progress and suggest a next
practice route. It must not claim or imply:

- adaptive diagnostics
- mastery decisions
- automatic sequencing
- grading
- summative assessment
- student-facing AI use
- PV projection
- PV machine promotion

Student-facing language should use practice wording such as `geoefend`,
`beschikbaar`, `volgende oefening`, and `ga verder`. Avoid `beheerst`,
`diagnose`, `niveau bepaald`, `geslaagd`, `gezakt`, or `score als cijfer`.

## Aspect Mapping

The platform MTU registry uses Dutch aspect labels. The shared engine exposes
student/product route filters in English-coded aspect names:

| Route filter | MTU aspects included | Default consumers |
|---|---|---|
| `reasoning` | `verbaal` | `Redeneren` |
| `calculation` | `rekenen` | `Rekenen` |
| `graphical` | `grafisch` | `Grafieken` |
| `mixed` | explicit multi-aspect view only | teacher/debug/advanced/checkpoint contexts |

Mixed-aspect skills may appear in more than one route when their MTU aspects
match the requested filter. If later data introduces a primary aspect, the
engine may prefer that for ranking, but this contract does not require new MTU
fields.

Examples:

- `A61` with `rekenen` + `verbaal` may appear in reasoning and calculation
  route contexts.
- `A62` and `A63` with `grafisch` appear in graphical route contexts.
- `A05` with `grafisch` + `rekenen` may appear in graphical and calculation
  routes.

## Display Modes

### `compact`

Purpose:

- reduce overload;
- answer `what should I practise now?`;
- support landing-page previews and exit-ticket checkpoint suggestions.

Rules:

- Show one primary recommendation when available.
- Show two to four available skills.
- Hide or collapse locked/not-yet-useful skills by default.
- Do not show the full catalog.
- Primary action: `Start oefenen` or `Ga verder`.
- Secondary actions: skill info and route details.

### `route`

Purpose:

- show the scoped path for one game/aspect;
- show prerequisites only as route context.

Rules:

- Filter by one requested aspect unless `mixed` is explicitly requested.
- Show prerequisite links needed to make the route understandable.
- Avoid unrelated future skills.
- Primary action stays on the current game.

### `full`

Purpose:

- teacher, advanced student, or debug inspection.

Rules:

- Never the default student-facing view.
- Must be explicitly opened.
- Should carry a visible label that this is a full overview, not a required
  sequence.

## State Semantics

Internal state names may include:

- `recommended`
- `available`
- `not_yet_useful`
- `in_progress`
- `practised`

If implementation needs legacy compatibility, `locked/open/completed` may be
kept internally, but student-facing labels must avoid mastery and sequencing
claims:

| Internal idea | Student-facing language |
|---|---|
| locked | later / nog niet nodig |
| open | beschikbaar |
| completed | geoefend |
| recommended | aanbevolen om nu te oefenen |

Stars/progress are local practice indicators only. They do not prove mastery,
unlock official routing, or authorize grading.

  surface: "graphical-game",
  mode: "route",

  skillScope: ["A61", "A62", "A63", "A38", "A39"],
  targetSkills: ["A61", "A62", "A63"],
  maxVisibleAvailable: 4,

## Consumer Requirements

### Redeneren

- Request `aspectFilter: "reasoning"`.
- Use verbal/procedure/causal skills as the default visible route.
- May include mixed skills only when the task asks students to explain or choose
  a calculation/procedure route.
- Must test causal/procedural reasoning, not recognition only.

### Rekenen

- Request `aspectFilter: "calculation"`.
- Use calculation/formula/unit/answer-field skills as the default route.
- Must support calculation field, final answer field, and unit where relevant.
- May include mixed skills when calculation needs source/table reasoning.

### Grafieken

- Request `aspectFilter: "graphical"`.
- Use graph/table/source-value/axis/visual-interpretation skills as the default
  route.
- Must include at least one later harder variant with less direct value
  labelling before broad graph-heavy scaling.
- May include mixed skills when graph reading feeds a calculation.

### Exit Ticket

- Request `mode: "compact"`.
- Use paragraph target skills only.
- Show touched skills and a next-practice suggestion.
- It may point students to `Redeneren`, `Rekenen`, or `Grafieken`.
- It must not grade, pass/fail, diagnose, decide mastery, or route
  automatically.

### Landing Page

- Request compact previews only.
- Show a controlled route: `Start`, `Leer`, `Oefen`, `Check`, `Verdiep`.
- Do not show all artifacts or all skills as peer cards.
- Full skill maps belong behind advanced/teacher/debug affordances only.

## Implementation Requirements For GAME-UX-1

Platform implementation should:

- expose MTU `aspects` through the skill-tree base elements;
- add aspect filtering to the skill-tree engine;
- add `compact`, `route`, and restricted `full` display modes;
- prevent `activeSkills: null` from becoming a default student game route;
- preserve existing local-stars behavior only as practice progress;
- add tests for aspect filtering, compact mode, route mode, and full-view
  restriction;
- add landing/game integration tests proving each game requests a scoped route;
- add screenshot or DOM checks for mobile, dark mode, and keyboard focus order;
- keep the current product-use boundaries false.

## L1.7C Readiness

L1.7C may start as a quality-upgrade sprint using this contract. It should not
attempt broad game scaling. If L1.7C needs the platform implementation before it
can inspect real game behavior, it must stop and route that dependency to
`GAME-UX-1` rather than inventing temporary per-game skill-tree UIs.
