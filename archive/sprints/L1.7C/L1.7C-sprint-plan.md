## Operationalized Sprint Procedure

1. Record this plan and the reusable game-row rubric before changing generated
   output.
2. Accept the GAME-UX-1 handoff only as platform runtime support. Stop if the
   sprint would import the untracked exit-ticket prototype or weaken blocked
   product-use boundaries.
3. Run the platform deploy workflow to refresh the Book 1 shared runtime and
   affected game surfaces so the lesson repo actually consumes GAME-UX-1.
   Do not hand-patch generated output.
4. Run focused game-row validation:
   - skill-map engine tests;
   - reasoning/procedure/graphical engine tests;
   - deploy/link/data checks if output changed;
   - paragraph validation for touched student-web surfaces;
   - Book 1 health if shared runtime or navigation changed.
5. Audit each game family against the rubric:
   - scoped skill-map route;
   - answer-revealing defaults;
   - feedback specificity;
   - scaffolding and final challenge;
   - calculation field / answer field / unit behavior;
   - graph-reading challenge difficulty;
   - causal/procedural reasoning depth;
   - mobile/dark/keyboard readiness;
   - product-use boundary language.
6. If the audit finds small generator/runtime defects, fix them in the platform
   source and regenerate through the workflow. If it finds larger design
   defects, record them as blockers and stop rather than pretending broad game
   scaling is safe.
7. Prepare review artifacts: baseline audit, technical QA, game-row quality
   matrix, and human-review packet if the sprint reaches review readiness.
8. Close L1.7C only if the required review records exist and the lead-review
   verdict allows closure. Otherwise keep L1.7C open with a clear stop state.

## Acceptance Criteria

- The deployed lesson runtime includes the shared skill-map engine or records a
  clear blocker if deployment is not safe.
- `Redeneren`, `Rekenen`, and `Grafieken` are each assessed against the rubric.
- Each game family has a disposition: `ready`, `revise`, or `held`.
- Any remaining MVP flags are visible and classified as fix-now, carry, or
  defer.
- No game exposes unfiltered full-skill views as the default student route.
- No game uses mastery, diagnostic, automatic sequencing, grading, summative,
  student-facing AI, PV projection, or PV machine-promotion language.
- Focused validators and relevant Book 1 checks pass after any regeneration.
- Human-review packet exists before any closure proposal.

## Stop Conditions

- Stop if generated output would need hand patching.
- Stop if the untracked exit-ticket prototype would need to be imported.
- Stop if game-row work would make mastery/diagnostic/adaptive/summative claims.
- Stop if the graph game cannot move beyond directly labelled scaffolded values
  without a larger design sprint.
- Stop if calculation/procedure surfaces cannot support calculation + answer +
  unit behavior without platform work outside this sprint.
- Stop if review evidence contradicts quality refs or roadmap claims.
